# 4.1. \[Crítico\] El watchdog puede provocar reinicios indefinidos sin llegar al apagado seguro

Este es probablemente el problema de software más importante.

El flujo es:

```
C++

```
wdt_enable(WDTO_8S);
```
```

Si el programa se bloquea, el watchdog reinicia el microcontrolador.

Pero después del reinicio:

```
C++

```
digitalWrite(RELAY, HIGH);
```
```

vuelve a activar el extractor.

Y el programa continúa funcionando.

Si el sensor o alguna condición externa provoca sistemáticamente:

> arranque → bloqueo → watchdog → reinicio → arranque → bloqueo...

el sistema puede permanecer indefinidamente en ese ciclo.

No existe un contador persistente del tipo:

> "tres watchdog resets consecutivos → fallo permanente → relé OFF".

El propio README presenta el watchdog como mecanismo de recuperación y el fallo persistente como condición de apagado, pero **un reinicio por watchdog no incrementa `contadorFallos`**.

### Consecuencia

\[Inferencia\] Un fallo que produzca un bloqueo repetitivo del firmware puede mantener el extractor funcionando indefinidamente.

No significa que vaya a ocurrir en condiciones normales, pero el mecanismo de protección no cubre realmente ese caso.

### Mejora

**Importante**

Registrar resets por watchdog en una variable persistente durante el ciclo de alimentación y establecer, por ejemplo:

> primer watchdog → recuperación  
> segundo watchdog → recuperación controlada  
> watchdog repetido → relé OFF

La implementación exacta dependería de cómo quieras tratar la pérdida de sensor.

## 6.2. Atención al punto de alimentación del Nano

El esquema parece alimentar el Nano directamente con 5 V regulados.

Eso es correcto para el pin de 5 V.

No sería equivalente introducir 5 V por VIN.

La documentación actual de Arduino especifica para el Nano clásico alimentación mediante USB o VIN, siendo VIN una entrada que pasa por el regulador; la documentación del modelo muestra 7–12 V como rango de VIN. [![](https://www.google.com/s2/favicons?domain=https://docs.arduino.cc&sz=128)Documentación de Arduino+1](https://docs.arduino.cc/resources/datasheets/A000005-datasheet.pdf?utm_source=chatgpt.com)

Por tanto:

**5 V regulados → pin 5V**

es la arquitectura que corresponde al esquema.

Esto debería quedar escrito explícitamente en la documentación.

-   RC snubber;
    
-   MOV/varistor;
    
-   otro supresor.

**Riesgo técnicamente plausible.**

No puedo afirmar que el relé vaya a fallar sin conocer el extractor y el relé.

Pero sí considero que la ausencia de esta información es una laguna de diseño eléctrico.

**Importante**

Documentar:

1.  modelo exacto del extractor;
    
2.  corriente nominal;

4.  modelo exacto del relé;

No añadiría un snubber arbitrariamente sin esos datos.

# 13\. Posible problema térmico del sensor

El sensor está colocado muy cerca del techo y del punto de iluminación.

Esto puede ser bueno para evitar contacto con agua directa, pero introduce una cuestión:

Eso afecta directamente a la humedad absoluta calculada.

No lo considero un defecto demostrado porque no hay mediciones comparativas.

Pero sería una comprobación experimental muy útil:

# 20\. El script `Serial_to_csv.py` tiene problemas de calidad

Este componente está bastante por debajo del nivel del firmware.

## Problema 1 — `strip(".txt")`

```
Python

Ejecutar

```
doc_name=input().strip(".txt")
```
```

`strip()` no elimina una extensión; elimina cualquiera de esos caracteres en los extremos.

Debería utilizarse algo equivalente a una operación explícita de extensión.

---

## Problema 2 — parser excesivamente dependiente del formato

Por ejemplo:

```
Python

Ejecutar

```
line.remove(item)
```
```

supone que cada token está presente exactamente donde se espera.

Un pequeño cambio en el texto del firmware puede romper el parser.

---

## Problema 3 — errores descartados

Este bloque:

```
Python

Ejecutar

```
ifline[3] =="Error":
    line= [15*index, 0, 0, 0, 0, line[-3]]
    continue
```
```

construye información sobre el error...

y acto seguido:

```
Python

Ejecutar

```
continue
```
```

hace que esa información **no se añada a `result`**.

Por tanto, el parser no conserva realmente las líneas de error en el CSV.

Eso es importante porque el propio proyecto utiliza esos datos para analizar la fiabilidad del sensor.

---

## Problema 4 — eventos de reset descartados

```
Python

Ejecutar

```
ifline[0] =="Nuevo": continue
```
```

también elimina la información sobre el reinicio del temporizador.

Eso hace que el CSV pierda información semánticamente importante.

---

## Problema 5 — tiempo reconstruido artificialmente

El parser utiliza:

```
Python

Ejecutar

```
15*index
```
```

en lugar del timestamp real.

Eso puede ser aceptable para reconstruir una gráfica, pero no es equivalente al tiempo real del controlador.

Especialmente problemático cuando hay:

-   errores;
    
-   reset del temporizador;
    
-   variaciones del tiempo de ejecución de las lecturas.
    

### Prioridad

**Conveniente**, pero si el Excel se utiliza como evidencia experimental formal, pasaría a **Importante**.

# 23\. Mejoras que sí haría

## Críticas

### 1\. Cerrar la seguridad eléctrica de la instalación

**Problema:** faltan datos para demostrar que fuente, relé, envolvente, cableado y ubicación son apropiados para una instalación permanente en baño.

**Cambio:** documentar y verificar componentes y protecciones reales.

**Beneficio:** poder distinguir un prototipo funcional de una instalación eléctrica realmente apta para uso continuado.

**Coste:** principalmente documental; posiblemente sustitución de componentes.

---

### 2\. Incorporar límite absoluto de funcionamiento

**Problema:** `TIEMPO_MAX` puede reiniciarse.

**Cambio:** separar timeout absoluto y timeout de una fase.

**Beneficio:** garantía real de tiempo máximo.

**Coste:** muy bajo.

---

### 3\. Gestionar watchdog repetido

**Problema:** bloqueo → watchdog → relé ON → bloqueo puede repetirse indefinidamente.

**Cambio:** contador de resets por watchdog y condición de apagado.

**Beneficio:** mejora importante de robustez.

**Coste:** muy bajo.

---

## Importantes

### 4\. Corregir el modelo de estadística del sensor

No porque la tasa de fallo sea necesariamente alta, sino para que la conclusión experimental sea correcta.

---

### 5\. Redefinir `contadorHumedadAlta`

Si la intención es detectar una subida continua, debe representar realmente una secuencia continua.

Si la intención es acumular "evidencia" de tendencia, entonces debe cambiarse el nombre y documentarse como tal.

---

### 6\. Revisar detección de sensor congelado

No la eliminaría.

La idea es buena.

Pero buscaría una forma de distinguir:

> sensor estable

de

> sensor bloqueado.

No introduciría simplemente un filtro más sofisticado sin evidencia de que lo necesites.

---

### 7\. Verificar protección del contacto del relé

No añadiría automáticamente un snubber.

Primero:

> modelo del extractor + modelo del relé.

Después se decide si hace falta y qué tipo.

---

### 8\. Repetir el experimento A/B

Esta es probablemente la mejora experimental con mayor relación información/esfuerzo.

No hace falta realizar 100 pruebas.

Un pequeño conjunto de repeticiones bajo condiciones similares ya permitiría saber si la diferencia observada es estable.

# 26\. Evaluación de la calidad de ingeniería

Mi lectura global es bastante clara:

### Como proyecto doméstico/experimental

Está **bien concebido**.

Especialmente en:

-   máquina de estados;
    
-   tratamiento de errores;
    
-   documentación;
    
-   utilización de humedad absoluta;
    
-   separación entre control manual y automático;
    
-   existencia de pruebas reales;
    
-   conservación de datos brutos;
    
-   watchdog;
    
-   límite temporal;
    
-   apagado definitivo.
    

No es un simple:

> `if humidity > X: fanOn`

con cuatro componentes.

Hay pensamiento de ingeniería detrás.

### Donde está menos maduro

La parte que más necesita mejorar no es la lógica básica, sino la transición entre:

> **prototipo electrónico funcional**

y

> **instalación eléctrica permanente en un baño**.

Ahí faltan muchos datos objetivos.

Y, dentro del software, hay una segunda capa de problemas: varias afirmaciones del README son ligeramente más fuertes que lo que realmente demuestra el código y los datos.

# 27\. Síntesis final

## Fortalezas principales

1.  **Arquitectura sencilla y adecuada al problema.**
    
2.  **Uso justificado de humedad absoluta.**
    
3.  **Máquina de estados clara.**
    
4.  **Buena atención a fallos del sensor.**
    
5.  **Watchdog correctamente considerado.**
    
6.  **Control manual independiente.**
    
7.  **Tiempo máximo incorporado.**
    
8.  **Datos reales y datos brutos disponibles.**
    
9.  **La metodología reconoce algunas limitaciones estadísticas.**
    
10.  **No se ha introducido complejidad tecnológica sin necesidad.**
    

---

## Debilidades principales

1.  El timeout máximo puede reiniciarse y dejar de ser máximo.
    
2.  Los watchdog resets no están integrados en el mecanismo de fallo persistente.
    
3.  La afirmación de seis mediciones independientes no es correcta.
    
4.  La estimación de la tasa de error del sensor no es estadísticamente sólida.
    
5.  El contador de aumento de humedad no implementa exactamente lo que dicen sus comentarios.
    
6.  La detección de sensor congelado puede confundir estabilidad con fallo.
    
7.  El ensayo A/B es insuficiente para cuantificar el efecto del extractor.
    
8.  El diseño eléctrico carece de datos suficientes para verificar completamente la instalación.
    
9.  El relé/carga inductiva necesita documentación mucho más precisa.
    
10.  La documentación contiene inconsistencias como UNO/Nano.
    
11.  El parser de datos pierde información relevante.
    

---

# Errores o decisiones cuestionables

Los que considero realmente relevantes son:

-   **"60 minutos máximos" cuando el temporizador puede reiniciarse.**
    
-   **"6 lecturas independientes" cuando realmente hay 3 adquisiciones del sensor.**
    
-   **"2 minutos de humedad creciente" cuando el contador no exige consecutividad.**
    
-   **estadística de 1,3 % basada en un modelo de seis lecturas independientes.**
    
-   **presentar los ensayos A/B como evidencia más fuerte de la que permiten n=1 y condiciones diferentes.**
    
-   **documentación eléctrica insuficiente para una instalación fija de 230 V en un baño.**
    

No considero errores:

-   usar Arduino Nano;
    
-   utilizar DHT22;
    
-   utilizar mediana;
    
-   utilizar humedad absoluta;
    
-   mantener control manual;
    
-   usar una máquina de estados;
    
-   apagar definitivamente el Arduino al acabar.

# Mejoras recomendadas por prioridad

### **Críticas**

1.  Verificar/documentar la instalación eléctrica real: fuente, relé, protecciones, envolventes, ubicación respecto a volúmenes del baño y cableado.
    
2.  Añadir un límite temporal absoluto independiente de los reinicios de `tiempoInicio`.
    
3.  Gestionar watchdog resets repetidos como una condición de fallo persistente.
    

### **Importantes**

4.  Corregir el modelo estadístico de las lecturas.
    
5.  Redefinir correctamente el contador de tendencia de humedad.
    
6.  Revisar el criterio de sensor congelado.
    
7.  Verificar el relé frente a la carga inductiva real.
    
8.  Repetir las pruebas A/B.
    
9.  Documentar exactamente los componentes eléctricos utilizados.
    

### **Convenientes**

10.  Corregir UNO/Nano.
    
11.  Mejorar parser y conservación de eventos.
    
12.  Documentar carcasa, montaje y condiciones térmicas.
    

### **Opcionales**

13.  PCB dedicada.
    
14.  SHT31/BME280.
    
15.  Configuración inalámbrica.
    
16.  Registro histórico.
    

No considero que 13–16 sean necesarias para solucionar los problemas fundamentales.

La arquitectura básica:

**interruptor manual → relé → extractor**

junto con:

**DHT22 → mediana → humedad absoluta + relativa → máquina de estados → apagado definitivo**

me parece una arquitectura razonable para el objetivo.

No veo una razón técnica suficiente para sustituirla por una arquitectura mucho más compleja.

# Preguntas pendientes que sí pueden cambiar la evaluación

Estas son las que considero realmente importantes:

1.  **¿Cuál es el modelo exacto del extractor?** Potencia, corriente y, si aparece en la documentación, tipo de motor.
    
2.  **¿Cuál es el modelo exacto del módulo de relé?** Especialmente especificación de contactos para cargas inductivas AC.
    
3.  **¿Cuál es la referencia exacta de la fuente de 5 V / 5 W?**
    
4.  **¿El montaje de Arduino y relé está dentro de una caja/envolvente? ¿Qué IP tiene?**
    
5.  **¿Cómo están realizadas físicamente las conexiones de 230 V: bornes, WAGO, PCB, soldadura, etc.?**
    
6.  **¿Dónde está exactamente el controlador respecto a la ducha y qué altura tiene el falso techo?**
    
7.  **¿El interruptor S1 realmente corta también la alimentación de la fuente de 5 V, como parece indicar el esquema?**
    
8.  **¿Qué versión de la librería `DHT.h` utilizaste al obtener los datos?** La conclusión sobre las tres adquisiciones se mantiene para la librería Adafruit actual, pero esto permitiría cerrar la trazabilidad.
    
9.  **¿Los datos de `Ducha_real_II.txt` proceden exactamente del firmware que está actualmente en el repositorio?**
    

Las cuatro primeras son especialmente importantes para poder cerrar la evaluación eléctrica.

## Conclusión

Mi conclusión provisional es que **el núcleo de ingeniería del proyecto es bastante más sólido de lo que aparenta un montaje doméstico**, sobre todo en la arquitectura de software y en la consideración de fallos. No veo motivos para complicarlo artificialmente.

Pero también hay una diferencia importante entre que el sistema **funcione** y que su diseño esté completamente cerrado desde el punto de vista de ingeniería.

Actualmente veo tres áreas que merecen atención real:

1.  **Seguridad y trazabilidad de la parte eléctrica de 230 V.**
    
2.  **Robustez ante fallos repetitivos del firmware/sensor.**
    
3.  **Rigor de la metodología experimental y de la interpretación estadística.**
    

Y hay un punto que considero especialmente claro: **el firmware y la documentación no coinciden completamente en la semántica de varios mecanismos de protección**. No es un problema estético; afecta a lo que realmente se puede afirmar sobre la robustez del sistema.

Si me proporcionas los **modelos exactos de fuente, relé y extractor**, y cómo está físicamente montada la parte de 230 V, puedo cerrar la parte eléctrica/normativa con bastante más precisión. En particular, ahí sí podremos determinar si lo que ahora es un **riesgo no verificado** se convierte en una conformidad demostrable o en un problema concreto.
